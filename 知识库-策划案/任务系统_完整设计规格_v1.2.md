# 任务系统
任务系统的定位与设计前提、任务加步骤的双层模型、步骤定义字段、状态机与流转规则、事件与谓词契约、作用域与领奖规则、标准任务数据结构，以及新手线七个主线任务的完整设计。具体条目与数值以任务配置表为准。

## 任务系统定位
任务系统是**编排层**。它只做四件事：
1. 接收战斗/背包/对话/修炼/突破等领域系统的事实变化
2. 按任务定义推进当前步骤/进度/状态
3. 调用导航/教学/演出/奖励/解锁/存档接口
4. 向 HUD/任务面板/NPC 标记提供任务视图

业务系统不感知"某任务是否存在"，只广播 `alchemy.recipe_completed`、`realm.changed` 等事实。任务、成就、奇珍录、灵兽记录、埋点和世界事件共享同一批事件源。

## 设计前提
- **开局身份**：玩家开局已是宗门弟子，删除 1.1「加入宗门」，新手线从 1.2 开始。
- **身份口径统一**：玩家开局已经是青冥宗外门弟子，境界为炼气第一层；服饰是外门常服奖励，不承担预备弟子转正。所有对白删除“刚拜入山门”“穿上才是正式弟子”等身份升级含义。
- **节点组织**：新手任务以大任务节点组织，节点内用步骤（Step）逐步引导，不引入“子任务”三级结构。
- 参考一念逍遥的新手流程作为节奏基准。

## 任务 + 步骤 双层模型
旧框架条件树只判"是否满足"，新手教学还要判"现在该教什么"，因此必须新增显式步骤机。

例：1.3 炼丹补授——到灵植园 → 药童对白 → 采集材料 → 周文扬对白 → 炼3颗符合当前境界的教学丹药 → 服1颗 → 调息完成。这些不能平铺进一个 `all` 条件树，否则玩家可能在教学前就满足后续条件。

## 层级裁定：二级（任务 + 步骤），不做三级子任务
设计前提里"每个大任务内穿插多个小任务"与模型里的 `QuestDef + StepDef` 存在歧义。**裁定：采用二级模型——`QuestDef`（任务）+ `StepDef[]`（步骤），不引入独立的"子任务"实体。** 理由：
- 存档：子任务若是独立实体，需各自 status/进度/领奖记录，存档字段翻倍；步骤只需 `currentStepId + stepProgress`，轻。
- 奖励：新手线是"整条完成给一次奖励 + 少量步骤即时反馈"，不需要子任务级独立领奖。
- UI：任务栏只显示"当前任务 + 当前步骤目标"，三级会让追踪列表层级过深。
- 前置：跨任务前置用 `completed_quest(taskId)`；步骤间顺序用 `nextStep`——两套已够，无需子任务前置。

术语统一：**"大任务节点"＝ Quest；"小任务/教学环节"＝ Step。** 全文"小任务"一律指 Step。若未来出现"一个 NPC 一次给多个可独立接取/放弃的委托"，那是多个 Quest，不是子任务。

## StepDef 字段定义（一）
| 字段 | 类型 | 取值 / 行为 |
|---|---|---|
| `stepId` | int | 任务内唯一，从 1 递增即为默认顺序 |
| `title` | string | 任务栏当前目标文案 |
| `objectiveMode` | enum | `SEQUENTIAL`（步骤内多目标须按序）/ `ALL`（全部满足即可，无序）/ `ANY`（任一满足）。**默认 `ALL`**；新手需强制手感顺序的用 `SEQUENTIAL` |
| `enterCondition` | RuleTree? | 进入本步骤的前置（缺省＝上一步 onComplete 即进入） |
| `objectives` | Predicate[] | 本步骤完成条件（复用 谓词），满足即步骤达成。每个目标须声明 `countMode`：`CUMULATIVE`（累计型，跨步骤总量）或 `STEP_LOCAL`（本步骤起算型，见下方 stepBaselines）|

## StepDef 字段定义（二）
| 字段 | 类型 | 取值 / 行为 |
|---|---|---|
| `onEnter` | Action[] | 进入时执行的动作序列，每个 Action 带执行语义（可重放/一次性），见下方定义 |
| `onComplete` | Action[] | 完成时执行：对白/解锁/即时反馈。**不在此发正式奖励**（正式奖励在任务 claim，走 ） |
| `deliveryRule` | struct? | 交付规则，见下。缺省＝步骤达成即完成，无需交付 |
| `failRule` | struct? | 失败/超时规则，见下。缺省＝不可失败 |

**`deliveryRule`（关键，绑定领奖原子顺序）**：`{ npcId, dialogueNodeId, mustInteract:bool }`。`mustInteract=true` 时即使 `objectives` 已满足，任务仍停在 `COMPLETABLE`，必须玩家到 `npcId` 触发 `dialogueNodeId` 才 `claim`。这正是修复迁移 bug⑨"交付可被绕过"的机制——交付是显式步骤条件，不靠 UI 约束。新手线凡"回 X 处交任务"的末步 `mustInteract=true`。

**`failRule`**：`{ kind: "TIMEOUT"|"DEATH"|"LEAVE_INSTANCE", onFail: "RESET_STEP"|"RESET_QUEST"|"RETRY_IN_PLACE" }`。新手线默认**不启用失败**；仅 1.8 心魔战用 `{DEATH, RETRY_IN_PLACE}`（原地重试、不重复扣材料）。限时/护送失败留后续扩展， 不做。

**`onEnter` Action 执行语义**：`onEnter` 会在断线重连、切场景恢复时按当前步骤重放，因此每个 Action 必须标类型：
| Action 类型 | 举例 | 重连行为 |
|---|---|---|
| `REPLAYABLE` 可重放 | 导航寻路、教学高亮、UI 提示、镜头指向 | 每次进入/重连都重放，无副作用 |
| `ONCE` 一次性 | 传送、功能解锁、剧情演出、发服饰/秘籍 | 首次执行后写 `doneActionIds[]`；重连时若已在集合内则跳过，**不重复传送/演出/解锁** |
| ❌ 禁止入 onEnter | 正式任务奖励 | 只能在 `tryClaim` 走 原子顺序结算，绝不放 onEnter/onComplete |

**`stepBaselines` 步骤基线**：任务级 `baseline_facts` 只解决"接取时刻起算"，不够——玩家可能在前置步骤里已顺手满足了后续步骤的事实。规则：
- `STEP_LOCAL` 目标：在**该步骤首次激活**时，把当前锚点值写入 `stepBaselines[stepId][depKey]`，之后进度 = 当前值 − 该步骤基线。
- `CUMULATIVE` 目标：不写步骤基线，用任务级 `baseline_facts`（接取起算）。
- **重连重放 `onEnter` 时不得重置 `stepBaselines`**（基线只在步骤首次激活写一次，存档持久化）。
- 默认：新手教学的计数目标（杀 4 只、炼 3 颗）用 `STEP_LOCAL`，保证"这一步现做现算"；跨任务的持有量/境界阈值用 `CUMULATIVE`。

## 状态机与流转规则
**生命周期（权威、存档）**：`NOT_ACCEPTED → ACCEPTED → COMPLETABLE → COMPLETED`，旁支 `ABANDONED`/`FAILED`（新手线不用）。**视图态（派生、不存档）**：`HIDDEN/VISIBLE/ACCEPTABLE/ACTIVE/COMPLETABLE/COMPLETED`，由（生命周期 + show/accept/complete 三态树）推导，沿用旧 `computeViewState`。领奖 `claimed` 与 `COMPLETED` 分离。

流转：接取 `tryAccept`（校验 accept 树 + 主线互斥）→ 步骤由 `objectives` 事实变化驱动推进 → 达成末步转 `COMPLETABLE` → `deliveryRule` 满足且 `tryClaim` → 执行领奖原子事务 → `COMPLETED` + 解锁后续。

**异常恢复规则**：
| 场景 | 恢复规则 |
|---|---|
| 断线重连 | 读快照 `status+currentStepId+stepProgress+baseline_facts+stepBaselines+doneActionIds`；重放当前步骤 `onEnter` 中的 `REPLAYABLE` 动作、跳过已记录的 `ONCE` 动作；**不重置 stepBaselines**；幂等键防重复发奖；`COMPLETABLE` 保留 |
| 玩家死亡 | 不清任务/步骤进度；副本内按 `failRule`（默认原地复活/重置波次） |
| 退出副本 | 副本步骤记录"已进入"事实；中途退出回退到"未进入副本"步骤 onEnter，不判失败 |
| 任务物品丢失 | 关键道具标记不可丢弃/出售；仍丢失则读档按"应持有量"补发（见待定项） |
| 重复触发/连点 | 接取/交付/领奖均过幂等键；已 COMPLETED 一次性任务不可再接 |

## 谓词版本归属与事件接口预留（一）
谓词分两半：**任务侧谓词实现**（写在任务系统内，成本低）与**领域侧事件广播**（要对应系统在完成点 `se.emit`）。二者版本可能不同——谓词能先写，但没有事件源就永远 UNKNOWN。规则：**谁的系统先做，谁负责在做的时候把事件接口一并埋好（哪怕当版任务还用不到）。**
| 谓词 | 依赖领域系统 | 系统版本 | 事件接口预留要求 |
|---|---|---|---|
| `cultivation.settled`/`realm.changed`/`breakthrough.finished` | 修炼/境界/突破 | | 做这些系统时，结算点直接 emit，不留后患 |
| `alchemy.recipe_completed`/`gather.completed` | 炼丹/采集 | | ** 做炼丹系统时**在"炼成/采完"点 emit； 若已要 1.5 打坐，打坐结算事件属修炼系统同批做 |

## 谓词版本归属与事件接口预留（二）
| 谓词 | 依赖领域系统 | 系统版本 | 事件接口预留要求 |
|---|---|---|---|
| `skill.proficiency_changed` | 功法神通 | | 做功法系统时在"熟练度变化"点 emit |
| `sect.contribution_changed` | 宗门 | | 做宗门系统时在"贡献变化"点 emit |

结论：**任务系统不提前替别的系统做事件广播**；但每个系统的详设 checklist 里要写死"完成点必须 emit 对应领域事件"，由本表约束。 只依赖 就绪的事件（combat/dialogue/region/item/quest），不依赖任何后置系统。

## 最小存档字段
`task_id / status / current_step_id / step_progress` · `claimed / completed_total / period_key / completed_in_period` · `instance_id / baseline_facts / updated_at / version` · **奖励幂等键**（防断线重登/重复点击/网络重试的二次扣料或二次发奖）。

## 领奖原子顺序
服务端校验当前步骤和交付 NPC → 原子扣除任务材料 → 写任务完成/领奖幂等记录 → 发奖或进补发邮件 → 保存 → 发 UI/播报事件。任何一步失败可回滚，幂等键保证重放不二次发奖。

## 主线任务 1.2「试炼幻境——首次击杀」·流程与操作
1. 陆青赠送储物袋，解锁背包格子并引导打开背包
2. 对话后将玩家与陆青传送至试炼幻境
3. 教学左键选中目标、右键攻击、QWER使用神通
4. 玩家击杀 4 只教学怪物
5. 教学靠近自动拾取、掉落光柱品质和首次掉落反馈
6. 玩家返回陆青处，打开背包查看战利品
7. 教学穿戴装备和服用药品
8. 陆青告知玩家前往灵植园寻找周文扬丹师

## 主线任务 1.2「试炼幻境——首次击杀」·异常处理
