## 当前任务表配置边界

`R任务表.xlsx` 的 `quest_config` 一行一项任务，`quest_step_config` 一行一个步骤，两表通过任务 ID 关联；首步骤由 `first_step` 指定，后续步骤只按 `next_step` 串联。`step_id` 是任务内稳定身份，不按大小决定流程顺序。两页均使用 `##var`、`##type`、`##group`、`##` 四行表头，枚举填中文别名。`##group` 留空的判定列同时导出给客户端与服务端，填 `c` 的文案、图标、表现列只导出给客户端。B 列“策划备注”不导出；数组槽位从第 1 个连续填写，已用槽位的每一格都要填，不适用的参数填 `0`，未使用的整槽留空，不得在已用槽位中留空导致后续列错位。

当前任务类型只有**主线、支线、悬赏**，同一时间只能进行一条主线。`quest_config` 提供前置任务 1～3、接取条件 1～3、自动接取、接取 NPC、首步骤、周期与任务奖励；`quest_step_config` 提供进入条件 1～3、目标 1～4、完成授予 1～3、末步交付及激活时的表现动作 1～4。正式任务奖励可配物品、修为、角色币和账号币；步骤完成可授予物品、背包或快捷栏扩容、功能解锁。步骤表现动作属于客户端展示，不承担授予或服务端判定。

自动接取只在登录、前置任务领奖、角色等级或大境界变化时检查；自动接取行的接取条件只能使用“任务已完成”“等级≥”“大境界≥”，`accept_npc` 必须为 0。需要持有物品、功能开放、与 NPC 交互等额外接取判定时，按主动接取设计。任务目标的“本步骤起算、接取起算、可回溯”按目标类别分别解释，详见 §4.2。

当前配置暂不开放每日／每周任务和采集目标；对话表及提示文本表未建，对话节点参数、交付对话节点和屏幕提示文本 ID 暂填 0。本文后续章节涉及世界／宗门任务、实例作用域、失败规则、邮件补发、功法路径熟练度等内容时，它们是后续设计目标或跨系统能力，不能仅凭本任务表直接配置投放。上述能力开放前须补齐配置入口和对应验收口径。

## 第一部分：架构层

### 1. 任务系统定位

任务系统是**编排层**。它只做四件事：

1. 接收战斗/背包/对话/修炼/突破等领域系统的事实变化
2. 按任务定义推进当前步骤/进度/状态
3. 调用导航/教学/演出/奖励/解锁/存档接口
4. 向 HUD/任务面板/NPC 标记提供任务视图

业务系统不感知"某任务是否存在"，只广播 `alchemy.recipe_completed`、`realm.changed` 等事实。任务、成就、奇珍录、灵兽记录、埋点和世界事件共享同一批事件源。

```
战斗/背包/对话/采集/炼丹/修炼/突破/宗门
                  ↓ 领域事件 (se.emit)
       玩家事实层（Fact / Anchor / DepKey）
                  ↓ 增量刷新
     QuestRuntime（状态 + 当前Step + 条件树 + 进度）
         ↓                 ↓                 ↓
      任务UI             奖励/解锁          存档/服务器同步
```

### 2. 设计前提

- **开局身份【已裁决】**：玩家开局已是宗门弟子，删除 1.1「加入宗门」，新手线从 1.2 开始。
- **身份口径统一【已裁决】**：玩家开局已经是青冥宗外门弟子，境界为炼气第一层；服饰是外门常服奖励，不承担预备弟子转正。所有对白删除“刚拜入山门”“穿上才是正式弟子”等身份升级含义。
- **节点组织**：新手任务以大任务节点组织，节点内用步骤（Step）逐步引导，不引入“子任务”三级结构。
- 参考一念逍遥的新手流程作为节奏基准。

### 4. 任务 + 步骤 双层模型

旧框架条件树只判"是否满足"，新手教学还要判"现在该教什么"，因此必须新增显式步骤机。

```
QuestDef
  ├─ taskId / type / prevQuests / acceptCond / autoAccept / acceptNpc / firstStep
  ├─ repeatPeriod / repeatLimit / rewardItems / rewardCult / rewardCurrency
  └─ StepDef[]
       ├─ questId / stepId / nextStep / title / objectiveMode
       ├─ enterCond / objectives（最多4项）
       ├─ actions（步骤激活时的客户端表现，最多4项）
       ├─ grants（步骤完成时的物品/扩容/功能解锁，最多3项）
       └─ deliverNpc / deliverDialogue / mustInteract（只用于末步）

QuestInstance
  ├─ status / currentStepId / stepProgress
  ├─ claimed / instanceId / baseline facts
  └─ updatedAt / version
```

例：1.3 炼丹补授——到灵植园 → 药童对白 → 采集材料 → 周文扬对白 → 炼3颗符合当前境界的教学丹药 → 服1颗 → 调息完成。这些不能平铺进一个 `all` 条件树，否则玩家可能在教学前就满足后续条件。

### 4.1 层级裁定：二级（任务 + 步骤），不做三级子任务【本版裁定】

设计前提里"每个大任务内穿插多个小任务"与模型里的 `QuestDef + StepDef` 存在歧义。**裁定：采用二级模型——`QuestDef`（任务）+ `StepDef[]`（步骤），不引入独立的"子任务"实体。** 理由：

- 存档：子任务若是独立实体，需各自 status/进度/领奖记录，存档字段翻倍；步骤只需 `currentStepId + stepProgress`，轻。
- 奖励：新手线是"整条完成给一次奖励 + 少量步骤即时反馈"，不需要子任务级独立领奖。
- UI：任务栏只显示"当前任务 + 当前步骤目标"，三级会让追踪列表层级过深。
- 前置：跨任务前置用 `completed_quest(taskId)`；步骤间顺序用 `nextStep`——两套已够，无需子任务前置。

术语统一：**"大任务节点"＝ Quest；"小任务/教学环节"＝ Step。** 全文"小任务"一律指 Step。若未来出现"一个 NPC 一次给多个可独立接取/放弃的委托"，那是多个 Quest，不是子任务。

### 4.2 StepDef 与 `quest_step_config` 字段对应

| 字段 | 类型 | 取值 / 行为 |
|---|---|---|
| `step_id` / `next_step` | int | `step_id` 在任务内唯一且稳定，不是顺序号；`next_step` 指向本任务下一步骤，末步填 0。`quest_config.first_step` 指向首步骤 |
| `title` | string | 任务栏当前目标文案 |

| 字段 | 类型 | 取值 / 行为 |
|---|---|---|
| `objective_mode` | enum | 填“全部／任一／顺序”；留空等于“全部”。顺序模式按目标槽位推进，持有类与阈值类轮到时按当前状态判断 |
| `enter_cond` | 条件槽位 1～3 | 多项为“并且”；不满足则等待进入，全空表示上一步完成即进入。当前谓词名单见本节后文 |

| 字段 | 类型 | 取值 / 行为 |
|---|---|---|
| `objectives` | 目标槽位 1～4 | 每槽填写稳定 `oid`、类型、`target`、`param`、`count`、击杀范围、计数起算；未用槽整槽留空。`oid` 不随槽位调整而重编号 |
| `actions` | 表现动作槽位 1～4 | 步骤激活时执行，仅客户端表现；每槽填写稳定动作 ID、类型、一次性、`target`、`param`，传送必须一次性 |

| 字段 | 类型 | 取值 / 行为 |
|---|---|---|
| `grants` | 授予槽位 1～3 | 步骤完成时授予物品、扩容或功能解锁；物品放不下时整次步骤完成失败。正式任务奖励仍在末步交付后的领奖流程中结算 |
| `deliver_npc` / `deliver_dialogue` / `must_interact` | 末步交付字段 | 只配在末步；需要 NPC 当面交付时 `deliver_npc` 非 0 且 `must_interact=TRUE`；节点表未建期间对话节点填 0 |

**末步交付**：`deliver_npc=0, must_interact=FALSE` 时目标达成后可在面板领奖；NPC 非 0 且 TRUE 时必须与该 NPC 交互；NPC 非 0 且 FALSE 时面板和 NPC 都可交付。NPC 为 0 却要求 TRUE 是配置错误。新手线明确写“回 X 处交任务”的末步配 NPC 和 TRUE，不能只靠导航或 UI 标记限制领奖。对话节点表未建期间 `deliver_dialogue=0`，只核对 NPC；待对话表接入后再开放精确节点校验。

**失败规则的边界**：旧案的 `failRule={kind,onFail}` 不在现行两张任务表的字段中。新手线默认不配置任务失败；1.8 心魔战“死亡后原地重试且不重复扣材料”仍是突破／副本流程需求，须由对应系统实现并单独验收，不能写成已经可由 `quest_step_config` 填出的失败规则。限时、护送失败同属后续扩展。

**步骤表现动作的恢复语义**：`actions` 在步骤激活时执行。一次性为 FALSE 的导航、高亮、提示、镜头动作可在重新进入或恢复任务时重放；一次性为 TRUE 的动作在同一次步骤激活中按稳定动作 ID 去重，传送必须填 TRUE。物品和功能解锁走 `grants`，不放在表现动作中：

| Action 类型 | 举例 | 重连行为 |
|---|---|---|
| `REPLAYABLE` 可重放 | 导航寻路、教学高亮、UI 提示、镜头指向 | 每次进入/重连都重放，无副作用 |
| `ONCE` 一次性 | 传送；确需仅播一次的客户端演出 | 同一次步骤激活按动作 ID 去重；玩家已在传送目标地图时不再传送 |

| Action 类型 | 举例 | 重连行为 |
|---|---|---|
| 不放入 `actions` | 物品、扩容、功能解锁、正式任务奖励 | 前三项在步骤完成时由 `grants` 授予；正式任务奖励在领奖时由 `quest_config` 结算 |

**目标计数基线**：任务级 `baseline_facts` 只解决“接取时刻起算”，步骤首次激活还需记录本步骤起算的基线。`quest_step_config.objectives[].count_mode` 使用下列中文枚举：

- “本步骤起算”：步骤首次激活时记录基线，事件类只算此后事件；持有物品／货币的进度是当前持有量减去该基线。
- “接取起算”：任务接取时记录基线，步骤激活前的新增事件或持有量变化也计入。到达区域、对话节点、客户端动作仍须目标开放后才计数，配此值等同本步骤起算。
- “可回溯”：持有物品／货币按当前总量判定，接取前已有的也计入；事件类不得配此值。等级、已学技能、熟练度、穿戴装备、完成任务等阈值类始终只看当前状态，不受三种起算值影响。
- **重连恢复表现动作时不得重置步骤基线**（基线只在步骤首次激活写一次，存档持久化）。
- 新手教学的计数目标（杀 4 只、炼 3 颗）配“本步骤起算”；跨步骤累计的新事件配“接取起算”；提前持有的材料是否可用，由该条目标显式选择“可回溯”或起算基线，不用一条全局规则代替。

### 4.3 状态机与流转规则【本版补：原文只写字段无规则】

**生命周期（权威、存档）**：`NOT_ACCEPTED → ACCEPTED → COMPLETABLE → COMPLETED`，旁支 `ABANDONED`/`FAILED`（新手线不用）。**视图态（派生、不存档）**：`HIDDEN/VISIBLE/ACCEPTABLE/ACTIVE/COMPLETABLE/COMPLETED`，由（生命周期 + show/accept/complete 三态树）推导，沿用旧 `computeViewState`。领奖 `claimed` 与 `COMPLETED` 分离。

流转：接取 `tryAccept`（校验接取条件 + 主线互斥）→ 按 `first_step`／`next_step` 推进步骤 → 达成末步转 `COMPLETABLE` → 按 `deliver_npc`／`must_interact` 校验交付并 `tryClaim` → 执行领奖原子事务 → `COMPLETED` + 解锁后续。

**异常恢复规则（原文完全缺失，必补）**：

| 场景 | 恢复规则 |
|---|---|
| 断线重连 | 读快照 `status+currentStepId+stepProgress+baseline_facts+stepBaselines+doneActionIds`；重放当前步骤可重放的 `actions`，跳过同一次激活中已执行的一次性动作；**不重置 stepBaselines**；幂等键防重复发奖；`COMPLETABLE` 保留 |
| 玩家死亡 | 不清任务／步骤进度；副本内原地重试或重置波次由副本／突破系统处理，现行任务表没有 `failRule` 字段 |

| 场景 | 恢复规则 |
|---|---|
| 退出副本 | 副本步骤的“已进入”事实与回退逻辑须由副本系统提供；现行任务表没有退出副本失败规则 |
| 任务物品丢失 | 关键道具保护及补救由物品／奖励系统定稿；现行任务表没有按“应持有量”自动补发的配置列（附录 B P1） |

| 场景 | 恢复规则 |
|---|---|
| 重复触发/连点 | 接取/交付/领奖均过幂等键；已 COMPLETED 一次性任务不可再接 |

### 4.4 事件公共信封【本版补：原文事件只有业务参数】

WAR3 的房间/副本/组队/镜像战会立刻依赖公共字段。**所有领域事件统一携带信封**：

```
EventEnvelope {
  playerId       // 事实归属玩家（组队/多人必需）
  scope          // 个人 / 房间 / 副本实例；决定事实写入哪个作用域
  instanceId?    // 副本/秘境实例 ID（1.2/1.4/1.8 镜像战按实例隔离）
  seq / ts       // 事件序号与时间戳（去重、乱序保护、离线批量结算排序）
  sourceEntity?  // 来源单位/NPC/掉落物（击杀归属、镜像战区分本体与分身）
} + 业务参数
```

约定：谓词 `resolveDeps` 与锚点键按需带 `scope`（如 `kill.monster.{id}@instance` vs `@personal`）；镜像战击杀只写副本实例作用域，不污染个人击杀事实。

**`seq / ts` 权威生成规则【本版补】**：`seq/ts` 必须由**主机/服务端权威生成**，按 `(playerId, scope)` 维度**单调递增**；**禁止**由客户端或单位本地时间生成。只有这样，击杀归属、断线补算、镜像/副本去重、离线批量结算排序才有唯一可信标准。乱序到达的事件按 `seq` 排序后再喂给事实层。

#### 5.1 谓词版本归属与事件接口预留【本版补】

谓词分两半：**任务侧谓词实现**（写在任务系统内，成本低）与**领域侧事件广播**（要对应系统在完成点 `se.emit`）。二者版本可能不同——谓词能先写，但没有事件源就永远 UNKNOWN。规则：**谁的系统先做，谁负责在做的时候把事件接口一并埋好（哪怕当版任务还用不到）。**

| 谓词 | 依赖领域系统 | 系统版本 | 事件接口预留要求 |
|---|---|---|---|
| `cultivation.settled`/`realm.changed`/`breakthrough.finished` | 修炼/境界/突破 | V2 | V2 做这些系统时，结算点直接 emit，不留后患 |
| `alchemy.recipe_completed`/`gather.completed` | 炼丹/采集 | V4 | **V4 做炼丹系统时**在"炼成/采完"点 emit；V2 若已要 1.5 打坐，打坐结算事件属修炼系统同批做 |

| 谓词 | 依赖领域系统 | 系统版本 | 事件接口预留要求 |
|---|---|---|---|
| `skill.proficiency_changed` | 功法神通 | V5 | V5 做功法系统时在"熟练度变化"点 emit |
| `sect.contribution_changed` | 宗门 | V5 | V5 做宗门系统时在"贡献变化"点 emit |

结论：**任务系统不提前替别的系统做事件广播**；但每个系统的详设 checklist 里要写死“完成点必须 emit 对应领域事件”。任务表没有开放的目标类型不得因运行时预留了事件名就提前配置；V1 的对话节点在对话表建立前只核对 NPC，不做精确节点判定。

### 5.2 现行任务表字段与目标白名单

**`quest_config`：**任务 ID 是稳定主键，不随剧情序号或上线顺序改动；主线、支线、悬赏分别建议从 100001、200001、300001 起编号。`prev_quests` 最多三个且全部完成才可接；`accept_cond` 最多三个且彼此为“并且”；`auto_accept=TRUE` 时仅可用“任务已完成、等级≥、大境界≥”作条件，接取 NPC 必须为 0。`first_step` 指向该任务的步骤 ID。同一时刻仅一条主线进行中。

接取与步骤进入条件共用的谓词只有：等级≥、大境界≥、任务已完成、任务进行中、持有物品≥、已学技能、功能已解锁。等级参数填角色等级，大境界参数填炼气至大乘的枚举值 1～8；“已学技能”填技能识别 ID，持有物品条件填物品 ID 与数量。任务自动接取还受上一段的三谓词限制。区域触发、持有货币和副本实例状态目前没有接取条件谓词，不得在配置栏填自造名称。

**`quest_step_config`：**每步 1～4 个目标，`objective_mode` 为“全部、任一、顺序”，留空按“全部”。每个目标的 `oid` 在步骤内稳定，从 1 编号；改变槽位顺序不改 `oid`。击杀范围填“同图”或“仅本人”；“同图”允许同地图在线队友击杀计入，非击杀目标也须填“同图”。目标类型及 `target`／`param`／`count` 口径如下：

| 类别 | 当前可配置的目标 | 配置与判定要点 |
|---|---|---|
| 战斗与获取 | 击杀怪物、拾取物品、获得物品 | 击杀填怪物 ID，可用 `param` 限定地图；拾取只计拾取成功，获得物品计一切进入角色所有权的路径；二者不能混写 |
| 持有与使用 | 持有物品、持有货币、使用物品、穿戴装备 | 持有物品读取综合背包与快捷栏；货币 `target` 填角色币 1 或账号币 2；使用物品计成功使用，包含服丹；穿戴装备只看当前装备位，`count=1` |

| 类别 | 当前可配置的目标 | 配置与判定要点 |
|---|---|---|
| 成长与修炼 | 学会技能、技能熟练度达到、等级达到、突破成功、打坐时长、获得修为、炼丹成功、完成任务 | 学会／熟练度目标填技能识别 ID；熟练度按本级值且技能须配“施放本神通”；等级目标填角色等级；打坐只计已结算秒数；炼丹成功按成品颗数 |
| 交互与引导 | 到达区域、对话节点、客户端动作 | 到达区域填地图 ID 与区域 ID；对话节点在对话表未建期间节点参数填 0、只核对 NPC；客户端动作只填当前白名单值 |

| 类别 | 当前可配置的目标 | 配置与判定要点 |
|---|---|---|
| 暂不开放 | 采集 | 采集事件来源未上线，不配置；将来按采集行为次数计，不能用持有物品量冒充 |

“可回溯”对持有类目标按当前总持有量计算；阈值类目标允许填写三种计数起算值，但始终只读当前状态，填“可回溯”也不改变结果；事件类目标不得填“可回溯”。到达区域、对话节点、客户端动作只在目标开放后计数；顺序模式下目标轮到时才开放。新手目标所需的先后顺序通过步骤链和目标模式保证，不按 `step_id` 大小推断。

**授予、表现与领奖：**步骤完成时 `grants` 最多三槽，类型为物品、扩容、功能解锁。配物品授予的步骤，其所有目标都必须属于“对话节点、到达区域、客户端动作”；授予物品放不下时整次步骤完成失败。扩容只支持综合背包（容器 1）和快捷物品栏（容器 6）。功能开放项目前只列任务面板 1、炼丹 2、悬赏委托 3、突破 4。表现动作最多四槽，在步骤激活时执行，当前支持导航 NPC／区域、传送、高亮界面、镜头看向 NPC、屏幕提示；传送必须一次性。高亮和“客户端动作”目标共用教学动作白名单：打开背包 1、打开任务栏 2、打开修炼面板 3、点击突破 4；超出白名单须先扩枚举。

任务领奖的 `reward_items` 最多四槽，另可发修为与最多两种货币奖励。正式任务奖励与步骤授予是不同入口；现行任务表没有直接发宗门贡献、称号、配方、功法的奖励列。周期列虽有一次性／每日／每周及北京时间重置规则，计划每日 05:00、每周一 05:00 重置，且未领奖的周期任务跨重置点作废；但当前每日、每周任务未开放，投放前只填“一次性”、`repeat_limit=0`。提示文本表未建时，表现动作“屏幕提示”的文本 ID 暂填 0。

#### 6.1 三种作用域

#### 6.2 最小存档字段

`task_id / status / current_step_id / step_progress` · `claimed / completed_total / period_key / completed_in_period` · `instance_id / baseline_facts / stepBaselines / updated_at / version` · **奖励幂等键**（防断线重登/重复点击/网络重试的二次扣料或二次发奖）。其中实例 ID、失败规则和事件作用域属于运行时方案，不是现行任务表字段。

#### 6.3 领奖原子顺序

步骤完成时先校验目标与授予容量；若物品授予放不下，本次步骤完成与授予一起失败，不产生部分发放。末步目标达成后按 `deliver_npc`、`must_interact` 校验交付，再对正式任务奖励执行幂等领奖；材料扣除属于相应玩法或另行明确的交付规则，不能从现行任务奖励列推导。正式领奖遇背包满是否采用邮件补发，当前任务表说明没有给出统一规则，须由奖励系统单独定稿，不能把步骤授予的失败口径改成邮件补发。
