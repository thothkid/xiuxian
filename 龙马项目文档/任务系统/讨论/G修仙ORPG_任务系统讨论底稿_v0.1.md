### 2.1 这条新手线真正要求的原子能力

- 对话与交付：任务前、中、后对白必须不同；“完成条件成立”和“已在NPC处交付”必须区分。
- 到达与导航：区域、NPC、场景、副本和返回点都要有稳定ID。
- 战斗与物品：击杀、掉落、拾取、持有量、使用、装备、秘籍学习都要能发领域事件。
- 生产与修炼：采集、炼丹、服丹、打坐、离线结算、熟练度、境界突破不是任务系统内部逻辑，而是任务监听的外部事实。
- 教学与演出：新手任务不是普通“满足条件即完成”；很多步骤有严格顺序，并要锁定或高亮UI。

## 3. 当前共识：任务系统是编排层，不是万能系统

【建议】任务系统只负责四件事：

1. 接收战斗、背包、对话、修炼、突破等领域系统的事实变化。
2. 根据任务定义推进当前步骤、进度和状态。
3. 调用导航、教学、演出、奖励、解锁和存档接口。
4. 向HUD、任务面板、NPC标记提供可显示的任务视图。

```text
战斗/背包/对话/采集/炼丹/修炼/突破/宗门
                  ↓ 领域事件
       玩家事实层（Fact / Anchor / DepKey）
                  ↓ 增量刷新
     QuestRuntime（状态 + 当前Step + 条件树 + 进度）
         ↓                 ↓                 ↓
      任务UI             奖励/解锁          存档/服务器同步
```

业务系统不应知道“某个任务是否存在”；它只广播诸如 `alchemy.recipe_completed`、`realm.changed` 这样的事实。任务、成就、图鉴、埋点、世界事件都可以订阅这些事实。

## 5. v0.1 事件与谓词契约

【建议】以下表格是本轮最值得继续讨论的核心。事件由领域系统广播；谓词由RuleTree调用；任务只写谓词和参数。

| 领域事件 | 事实/谓词示例 | 主要任务 | 说明 |
|---|---|---|---|
| `dialogue.node_completed` | `dialogue_node_completed(npcId, dialogueId, nodeId)` | 1.1—1.8 | 对话完成是严格任务事实，不是“打开过对话框”。 |
| `region.entered` / `movement.arrived` | `arrived_at_region(sceneId, rectId)` | 1.1、1.3—1.8 | 区域与场景都用配置ID。 |
| `combat.unit_killed` | `kill_count_ge(monsterId, count, scope)` | 1.2、1.6、1.7、1.8 | `scope` 区分个人、房间、实例；BOSS和镜像要可过滤。 |
| `item.changed` | `item_count_ge(itemId, count, inventoryScope)` | 1.2、1.7 | 持有型目标；是否提前持有可计入需裁决。 |
| `drop.picked` | `pickup_count_ge(itemId, count)` | 1.2 | 和“当前持有量”不同，适合首次拾取教学。 |
| `gather.completed` | `gather_count_ge(nodeType/itemId, count)` | 1.3、1.7 | 采集行为与最终持有量可分别判定。 |
| `alchemy.recipe_completed` | `recipe_crafted_ge(recipeId, count)` | 1.3 | 以配方/产物ID判定，不以背包里恰好有丹药代替。 |
| `item.used` / `item.equipped` | `item_used_ge`、`equipment_equipped`、`manual_learned` | 1.2—1.5 | 背包解锁、穿戴、服丹、秘籍激活。 |
| `cultivation.settled` | `meditation_duration_ge`、`cult_ge` | 1.3、1.5、1.7 | 在线每3秒或离线批量结算；任务不订阅每帧。 |
| `skill.proficiency_changed` | `proficiency_ge(skillId, value)` | 1.4 | 功法学习与熟练度增长分开。 |
| `bounty.turned_in` | `bounty_completed`、`turn_in_at_npc` | 1.6 | 新手首单必须固定可用，不能被日刷随机池顶掉。 |
| `realm.changed` | `realm_ge(realm, subLevel)` | 1.7 | 炼气九层/圆满由境界系统权威发出。 |
| `breakthrough.finished` | `breakthrough_result(id, success)` | 1.8 | 首次保底、心魔、雷劫和晋升都在突破系统结算。 |
| `quest.claimed` | `completed_quest(taskId)` | 全链 | 作为后续任务显示/接取条件。 |

## 6. 新手任务必须采用“任务 + 步骤”双层模型

【建议】旧框架的条件树能判断“是否满足”，但新手教学还要判断“现在该教什么”。因此要增加显式步骤。

```text
QuestDef
  ├─ taskId / category / scope / trigger / repeat / rewards
  └─ StepDef[]
       ├─ stepId / title / objectiveMode
       ├─ enterCondition / objectives
       ├─ onEnter（导航、教学、传送、演出）
       ├─ onComplete（对白、解锁、下一步骤）
       └─ deliveryRule / failRule

QuestInstance
  ├─ status
  ├─ currentStepId
  ├─ stepProgress
  ├─ claimed / instanceId
  ├─ baseline facts
  └─ updatedAt / version
```

例如 1.3 应顺序执行：到灵植园 → 药童对白 → 采集凝露草 → 周文扬对白 → 炼制3颗引气丹 → 使用1颗 → 调息完成。不能把这些目标全塞进一个 `all` 条件，否则玩家可能在教学前就满足后续条件。

## 7. 作用域、存档与领奖规则

### 7.1 三种作用域

| 作用域 | 适用内容 | 例子 |
|---|---|---|
| 个人存档 | 主线、突破材料、首次筑基、独有BOSS、教学解锁 | 1.1—1.8 的主进度。 |
| 房间实例 | 普通怪击杀、普通掉落、可组队悬赏、临时副本 | 1.2/1.4 的副本战斗、部分1.6悬赏。 |
| 全服表现 | 世界播报、活动状态、排行榜 | 1.8筑基播报；不是任务完成事实。 |

### 7.2 最小存档字段

- `task_id`、`status`、`current_step_id`、`step_progress`。
- `claimed`、`completed_total`、`period_key`、`completed_in_period`。
- `instance_id`、`baseline_facts`、`updated_at`、`version`。
- 奖励流水/幂等键：防止断线重登、重复点击、网络重试时二次扣料或二次发奖。

### 7.3 领奖顺序

推荐顺序：**服务端校验当前步骤和交付NPC → 原子扣除任务材料 → 写任务完成/领奖幂等记录 → 发奖或进入补发邮件 → 保存 → 发UI/播报事件**。

## 10. 下一轮讨论的建议顺序

1. 先裁决第9节的 P0 六项，不讨论具体代码。
2. 用裁决结果定义 `QuestDef / StepDef / QuestInstance` 的字段草案。
3. 以任务1.1和1.2做最小纸面/灰盒流程：事件、步骤、状态、存档点、UI提示逐项走通。
4. 再把1.3—1.8按相同模板展开，确认炼丹、打坐、突破等系统的事件契约。
5. 最后才讨论宗门任务、悬赏池、日常/周常和世界事件的扩张规则。

## 结论

**本项目不需要重新发明任务系统。**应以旧项目的配置、RuleTree、事件依赖刷新、快照、奖励和UI组织方式为底座，新增修仙领域事件与显式步骤机。当前最重要的不是继续堆监听类型，而是先把开局叙事、步骤顺序、提前计数、NPC交付和首次突破这五个产品规则定死。
