## 2. 共识：任务系统是"编排层"，不是万能系统

【建议】任务系统只做四件事：① 接收战斗/背包/对话/修炼/突破等领域系统的事实变化；② 按任务定义推进当前步骤/进度/状态；③ 调导航/教学/演出/奖励/解锁/存档接口；④ 向HUD/任务面板/NPC标记提供任务视图。

```text
战斗/背包/对话/采集/炼丹/修炼/突破/宗门
                  ↓ 领域事件(se.emit)
       玩家事实层（Fact / Anchor / DepKey）
                  ↓ 增量刷新
     QuestRuntime（状态 + 当前Step + 条件树 + 进度）
         ↓                 ↓                 ↓
      任务UI             奖励/解锁          存档/服务器同步
```

业务系统**不应知道"某任务是否存在"**，只广播 `alchemy.recipe_completed`、`realm.changed` 这样的事实；任务、成就、图鉴、埋点、世界事件都可订阅同一批事实。

## 5. 任务 + 步骤 双层模型（新手线必需）

【建议】旧框架条件树只判"是否满足"，新手教学还要判"现在该教什么"，故增显式步骤：

```text
QuestDef
  ├─ taskId / category / scope / trigger / repeat / rewards
  └─ StepDef[]
       ├─ stepId / title / objectiveMode
       ├─ enterCondition / objectives
       ├─ onEnter（导航/教学/传送/演出）
       ├─ onComplete（对白/解锁/下一步骤）
       └─ deliveryRule / failRule
QuestInstance
  ├─ status / currentStepId / stepProgress
  ├─ claimed / instanceId / baseline facts
  └─ updatedAt / version
```

例 1.3 顺序执行：到灵植园 → 药童对白 → 采集凝露草 → 周文扬对白 → 炼3颗引气丹 → 服1颗 → 调息完成。不能把这些平铺进一棵 `all`，否则玩家可能在教学前就满足后续条件。

## 6. 作用域、存档与领奖规则

### 6.1 三种作用域

| 作用域 | 适用内容 | 例子 |
|---|---|---|
| 个人存档 | 主线、突破材料、首次筑基、独有BOSS、教学解锁 | 1.1—1.8 主进度 |
| 房间实例 | 普通怪击杀、普通掉落、可组队悬赏、临时副本 | 1.2/1.4 副本、部分 1.6 悬赏 |
| 全服表现 | 世界播报、活动状态、排行榜 | 1.8 筑基播报（**非任务完成事实**） |

### 6.2 最小存档字段

`task_id/status/current_step_id/step_progress` · `claimed/completed_total/period_key/completed_in_period` · `instance_id/baseline_facts/updated_at/version` · **奖励幂等键**（防断线重登/重复点击/网络重试的二次扣料或二次发奖）。

### 6.3 领奖原子顺序（强约束）

**服务端校验当前步骤和交付NPC → 原子扣除任务材料 → 写任务完成/领奖幂等记录 → 发奖或进补发邮件 → 保存 → 发UI/播报事件**。任何一步失败可回滚，且幂等键保证重放不二次发奖。

## 7. 版本路线、V0 边界（P01 修正）与拆分表缺口

### 7.1 V0 任务切片 = 仅"存档字段预留"，引擎下沉 V1【已裁决/依据P01】

P01 是 V0 边界权威：V0 正面清单 10 项＝灰盒最小闭环（房间/建角/属性/战斗/怪物/掉落/背包/存档/配置加载/UI），**不含任务系统**；P01 §1.4 明列「需完整内容才有效果的系统（境界突破/炼丹/**任务**）一律后置」；Nope 清单「剧情｜任务/引导/NPC…｜归入 V1/V5」。因此：

- **V0 之于任务：不移植引擎、不接任务表、不跑任务。唯一动作＝按 P01「存档一次定型」原则，在 V0 存档结构里预留任务占位字段**（与现有命格/道器/轮回占位同级，占位 int/空表，已考虑后续扩展）。这样 V1 起任务系统落盘不必迁移旧档。
- 引擎移植（RuleTree/QuestService/Anchor/谓词）+ StepRuntime + 追踪UI + 新手 1.1/1.2 → **V1**（P01：V1=新手村；剧情/引导→V1）。

> 说明：小C 上一版把"V0 跑 GM 测试任务"写进 V0 属越界，本版按 P01 收回。RuleTree 引擎作为底座 A8(P0) 基建，若团队愿意可在 V0 以纯 dev 单元测试形式先行验证，但**不作为 V0 交付项、不产出可玩/GM 任务线**。

### 7.2 新手线跨版本依赖（整体规划关键）

新手 1.1–1.8 依赖的系统横跨 V1–V5，**完整新手线不可能一版做完**，需按依赖系统就绪度分批接入：

| 任务 | 依赖系统 | 最早可落地版本 |
|---|---|---|
| 1.1 加入宗门 | 对话/移动/到达/导航 | **V1** |
| 1.2 首次击杀 | 战斗/掉落/背包/基础穿戴 | **V1** |
| 1.5 打坐修为 | 修炼/修为/离线 | **V2** |
| 1.7 收集突破材料 | 境界/BOSS掉落 | **V2** |
| 1.8 破境筑基 | 突破/心魔/雷劫 | **V2** |
| 1.3 首次炼丹 | 采集 + 炼丹 | **V4**（P01：炼丹→V4） |
| 1.4 传授功法 | 功法神通 | **V5**（底座：P功法→V5） |
| 1.6 首次委托 | 任务系统自身 + 悬赏池 | V1 框架就绪，内容 V1+ |

**规划结论**：任务**框架** V1 即可就绪并跑通 1.1/1.2；1.5/1.7/1.8 随 V2 修炼突破补齐；**完整八任务链要到 V4/V5 系统就位后才能全程无占位跑通**。可选：为炼丹(1.3)/功法(1.4)在早期版本做"简化占位实现"以让新手线不断链，但需策划确认是否接受占位。

### 7.3 《工作任务拆分表》缺口（需补排期）

250 条工作项里任务相关**只有 6 条且全挂 AE 引导名下**（AE-001/002 新手引导+箭头、AE-003 首次突破引导、AE-004/005/006 师门/日常/周常），全表无 `RuleTree/条件树/状态机/事件总线/任务面板`——**任务引擎内核零排期**。建议补：

- `QUEST-CORE-01`（**V1**，核心层）移植 QuestSystem 内核：RuleTree三态引擎 + Anchor + 双层状态机 + rev增量快照，**并修 bug③④⑤⑥⑦**。
- `QUEST-CORE-02`（**V1**，核心层）谓词最小集(kill/completed_quest/dialogue/arrived/item)+`_init`注册，`find_target_npc` 重写。
- `QUEST-STEP-01`（**V1**，核心层）StepRuntime + 步骤存档/恢复。
- `QUEST-UI-01`（**V1**，UI层）任务追踪HUD + 任务面板 + NPC头顶气泡(接G3)。
- `QUEST-FLOW-01`（**V1**）新手 1.1/1.2 全链配置；`QUEST-FLOW-02`（**V2**）1.5/1.7/1.8；1.3/1.4 随 V4/V5。
- `QUEST-SAVE-00`（**V0**，核心层）**仅**在存档结构预留任务占位字段（唯一的 V0 任务项）。

## 9. 下一轮建议议程

1. 先裁决 §8.2 的 P0 五项（不讨论代码）。
2. 用裁决结果定 `QuestDef / StepDef / QuestInstance` 字段草案，并据此定 §7.1 中 V0 要预留的任务存档占位字段清单。
3. 以任务 1.1、1.2 做最小纸面/灰盒流程：事件、步骤、状态、存档点、UI提示逐项走通（对应 V1 首批交付）。
4. 再把 1.5/1.7/1.8 按同模板展开（V2），确认修炼/境界/突破事件契约。
5. 最后讨论炼丹/功法占位(1.3/1.4)、宗门任务、悬赏池、日常/周常、世界事件的扩张规则。

## 结论

**本项目不需要重新发明任务系统。** 以旧 QuestSystem 的配置/RuleTree/事件依赖刷新/快照/奖励/UI 为底座，新增修仙领域事件与显式步骤机。**V0 只在存档里给任务留占位字段，引擎与新手线从 V1 起做**；完整八任务链因跨 V1–V5 系统依赖需分批落地。当前最要紧的不是继续堆监听类型，而是先把 §8.2 五条 P0（1.8入口、步骤顺序、提前计数、NPC交付、首次突破规则）定死。
