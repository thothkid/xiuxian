# 修仙 ORPG · 任务系统融合基线 v1.1

> 用途：作为后续任务系统讨论与实现的共同底稿。本文以《C任务系统_优化基线_v1》为主骨架，吸收旧项目代码核验结论与审核修正；不改写截图原文，也不把未确认的剧情、数值当成既定设计。

## 0. 本版已锁定的口径

- **开局定位：加入宗门。** 新玩家由宗门身份进入游戏；拜入何宗、接引人、对白和奖励数值暂不影响框架，可后配。
- **不纳入：VIP、杀怪抽奖及其概率/货币逻辑。** 旧项目“击杀事件”里混入的这类业务，只作为历史耦合案例，不复用、不迁移。
- 任务原始内容以小 C 的截图逐字提取为事实来源；本文只讨论其暴露出的任务能力与系统实现，不对原文润色或纠错。
- 当前先搭可跑、可存档、可扩展的通用骨架；怪物 ID、物品 ID、NPC 文案、奖励数值、悬赏轮次等细节均可后配，不阻塞实现。

## 1. 新手链包含的任务与能力

| 编号 | 任务名（按提取稿） | 主要玩家动作 | 任务系统需要支持的能力 |
|---|---|---|---|
| 1.1 | 加入宗门 | 对话、移动、进区域、获得身份/物品 | 接取、NPC 对话、区域到达、物品授予、完成后解锁 |
| 1.2 | 仙境试炼 | 跟随、对话、移动、战斗教学 | 对话推进、区域引导、可选战斗目标 |
| 1.3 | 寻觅师兄 | 移动、找 NPC、对话、跟随 | 多 NPC 对话、导航、阶段推进 |
| 1.4 | 长老授业 - 传授功法 | 对话、学习/装备功法、试用 | 功法事件、引导步骤、一次性奖励 |
| 1.5 | 再遇陆青 - 修炼基本功 | 打怪、收集、修炼/装备 | 击杀计数、物品收集、装备或修炼事件、目标进度 |
| 1.6 | 历练委托 - 首次交托任务接取 | 接取委托、击杀、交付 | 前置任务、任务接取、击杀、交付/领奖、任务板或 NPC |
| 1.7 | 鸡妖之路 - 收集突破材料 | 击杀、掉落收集、交付 | 指定怪击杀、材料计数、背包校验与扣除、突破前置 |
| 1.8 | 蜂巢筑基 - 首次大境界突破 | 战斗、收集、突破 | 大境界事件、条件聚合、完成演出/奖励、后续内容解锁 |

这八项不应被做成八套脚本。它们可归为四类可组合步骤：

1. **交互步骤**：对话、接取、领取、确认、交付。
2. **世界步骤**：到达区域、找到 NPC、跟随或护送。
3. **成长步骤**：击杀、收集、装备功法、修炼、突破。
4. **编排步骤**：前置完成、自动解锁、奖励、阶段顺序、失败/重试（后续需要时）。

## 2. 面向 WAR3 的总体框架

```text
WAR3 原生/项目事件
        ↓
事件适配层（统一事件名与参数）
        ↓
事实层 Fact / Anchor（按玩家保存当前事实）
        ↓
条件与步骤运行时（只刷新受影响任务）
        ↓
任务生命周期、奖励、UI、存档
```

### 2.1 三个必须分开的状态

| 状态 | 作用 | 示例 |
|---|---|---|
| 事实状态 | 玩家在世界中已经发生的事 | 击杀数、背包材料数、当前境界、是否学会功法 |
| 任务生命周期 | 任务处于什么阶段 | 未接取、进行中、可提交、已完成 |
| 视图状态 | UI 该如何呈现 | 隐藏、可接、追踪中、可交、已完成 |

不能用 UI 是否显示来代替任务是否完成；也不能用一次对话回调直接写奖励来代替“条件满足 → 可交 → 领奖”的任务流程。

### 2.2 推荐的职责边界

- **事件适配层**：把项目现有中文事件或 WAR3 原生触发转为稳定的语义事件；业务系统不直接遍历所有任务。
- **Fact / Anchor**：保存“某玩家已击杀何种怪多少只”“背包内某物有多少”“是否完成任务 X”等可查询事实。
- **QuestService**：按玩家管理任务实例、前置、步骤推进、存档、奖励和 UI 刷新。
- **Predicate / RuleTree**：把“击杀 10 只”“材料达到 3 个”“完成前置”“境界达到筑基”等写成可组合条件。
- **StepRuntime**：处理有顺序的复合任务。1.3、1.4、1.5 至少需要它；不能只靠单个条件树。
- **RewardService**：统一结算，保证重复点击、重连与读档后不会重复发奖。

## 3. 旧项目可复用的基础与不应照搬的部分

旧项目代码位置：`E:\works\legendary-map\War3ORPGMap\src\map\QuestSystem`。

| 旧项目已有内容 | 结论 | 本项目处理方式 |
|---|---|---|
| 每玩家 `TaskService`、任务定义、任务实例、快照/增量 | 可复用 | 保留分层与服务边界，先做读写回归测试 |
| `RuleTree`、条件工厂、事实锚点 | 可复用 | 用作通用前置与目标条件基础 |
| `kill_count_ge`、`collect_items`、`completed_quest` 等条件 | 可复用 | 改为统一事件适配和事实更新；补齐收集进度 UI |
| 主线互斥、任务面板、NPC 导航、GM/API | 可复用 | 保留，按修仙 UI 和宗门入口调整 |
| `player_level_ge`、强化、装备等条件 | 按系统接入 | 仅在对应成长系统实际存在后开启 |
| 任务多步流程 | 缺口 | 新增 `StepRuntime`，支持顺序、当前步骤与步骤完成事实 |
| `find_target_npc`、`recycle_equipment_count` | 未形成有效闭环 | 不迁移，等有实际事件和验收场景再做 |
| 周期任务导入 | 有分类风险 | 本期不引入日/周任务内容；未来单独校验分类与重置语义 |
| 击杀触发内的 VIP/抽奖/概率逻辑 | 业务耦合 | 明确删除；击杀监听只负责更新事实并通知受影响任务 |

### 3.1 需要先核验而非直接假定的旧存档风险

旧实现中，读取任务快照时使用 `task_{id}` 形式查找，而完整快照写入处使用数值 ID 键。它是否在实际序列化后出错，取决于外层序列化行为；因此结论应是：

- 在迁移或复用前，补一组“接取 → 推进 → 存档 → 读档 → 领奖”的自动/GM 回归测试；
- 统一快照键格式、版本号、玩家作用域和向后兼容策略；
- 测试通过前，不把旧快照协议视为可直接沿用。

## 4. 事件与条件：按阶段接入

事件名称是新系统对外语义名；内部可以继续由现有中文 `se` 事件或 WAR3 原生触发适配而来。

| 语义事件 / 条件 | 用途 | 优先级 |
|---|---|---|
| `quest.claimed` / `completed_quest` | 前置完成、后续自动解锁 | V0 |
| `combat.unit_killed` / `kill_count_ge` | 试炼、历练、材料怪击杀 | V0 |
| `item.changed` / `collect_items` | 收集、交付前背包校验 | V0；V1 完善 UI |
| `dialogue.finished` | 加入宗门、授业、接取与交付 | V1 |
| `region.entered` | 入门、试炼、找人、剧情触发 | V1 |
| `quest.step_completed` | 多步骤串联 | V1 |
| `skill.learned`、`skill.equipped` | 传授功法、功法试用 | V2 |
| `cultivation.changed`、`realm.breakthrough` | 修炼、炼气/筑基等突破 | V2 |
| `npc.interacted`、`escort.finished`、`boss.killed` | 找 NPC、护送、首领任务 | 按内容需要 |
| 日/周重置、限时、队伍共享进度 | 周期/活动任务 | 后续版本 |

原则：一次事件只更新相关事实，并只刷新订阅该事实的任务；不要在任意击杀后全量扫描所有玩家的所有任务。

## 5. 数据与运行时的最小模型

### 5.1 任务定义应包含的稳定语义

- `id`、任务类别、名称、描述、NPC/区域锚点；
- 显示条件、接取条件、完成条件、前置任务；
- 重复规则（一次性、可重复、周期性）；
- 奖励表和奖励领取状态；
- 可扩展的步骤描述或 `extra` 字段。

### 5.2 任务实例应保存的内容

- 玩家 ID、任务 ID、生命周期与视图状态；
- 当前步骤索引、各步骤进度、已完成步骤；
- 接取/完成/领奖时间与防重领奖标记；
- 任务快照版本、定义版本或迁移标记。

### 5.3 StepRuntime 的最小职责

```text
任务接取
  → 激活当前步骤
  → 监听该步骤依赖的事实
  → 条件满足，记录步骤完成
  → 切换到下一步骤或使任务可交
  → 统一领奖并写入 completed_quest
```

V1 先支持“线性步骤”；分支、失败、限时、护送失败等能力留为扩展，不预先做复杂状态机。

## 6. V0：仅做可验证的技术闭环，不上玩家任务内容

按项目分期，V0 的目标是最小可玩循环，不承诺可见的新手剧情或任务配置。若 V0 启动任务模块，范围应严格限定为一个 GM/测试闭环：

```text
GM 接取测试任务 A
  → 击杀 N 个测试怪
  → 领取一次测试奖励
  → 写入 completed_quest(A)
  → 自动解锁测试任务 B
  → 收集 1 个测试物品（或设置测试事实）
  → 提交 B，存档并读档验证状态
```

这里不使用 `player_level_ge` 作为链路前置：V0 尚未形成可依赖的成长等级链。测试任务 B 优先用“收集测试物品”验证背包事实；若该监听尚未接入，可暂用明确的 GM 测试事实替代，但不得把替代方案当成正式内容能力。

### 6.1 V0 必须冻结的不是表格细节，而是语义契约

1. 事件语义名、最小参数和玩家归属规则。
2. Fact/Anchor 键命名、持久化类型与依赖订阅方式。
3. 任务生命周期、视图状态、`completed_quest` 的含义。
4. 快照键格式、版本、玩家作用域与读档验证标准。
5. 奖励的幂等规则：一次完成只能结算一次。

`steps[]` 的完整物理字段结构不在 V0 过早冻结；只保留扩展位，等 V1 的线性步骤跑通后再定型。

### 6.2 V0 验收线

- 两个测试任务可接取、推进、完成、领奖与前置解锁；
- 击杀仅更新该玩家、该怪物对应的事实；
- 物品变化可正确影响收集条件；
- 重复领奖无效；
- 存档后读回任务状态、进度、奖励状态与前置事实一致；
- 不包含 VIP、抽奖、概率奖励等无关业务逻辑。

## 7. 后续落地顺序

| 阶段 | 交付重点 | 对应内容 |
|---|---|---|
| V0 | 后台任务技术闭环 | GM 测试 A/B、事件/存档/奖励契约 |
| V1 | 宗门开局与基础引导 | 1.1 加入宗门、1.2 仙境试炼；对话、区域、导航、线性步骤 |
| V2 | 修仙成长与历练链 | 1.3–1.8；功法、修炼、击杀、收集、交付、突破事件 |
| 后续 | 可重复和内容运营能力 | 悬赏池、日/周任务、活动、队伍共享、限时与失败处理 |

## 8. 当前无需阻塞的细节

以下内容应记录在内容配置或策划表中，等系统骨架可验证后补齐：宗门名称与入门对白、接引 NPC、怪物与材料 ID、击杀数量、奖励数值、功法名称、悬赏轮次、筑基演出、UI 美术与文案。

它们不影响本版已经确定的核心：**宗门开局 → 事件产生事实 → 任务按步骤消费事实 → 幂等奖励 → 存档可恢复 → 前置解锁后续内容。**
