## 四、结构问题详解 / Details

### 4.1 速率字段的时间单位没有声明

以下字段都表示「单位时间多少」，但表上没有任何地方声明这个单位是什么：

| 中文名 / Chinese | 英文字段 / Field | 所在表 / Table |
|---|---|---|
| 基础修为速率 | `base_cult_rate` | 境界等级配置表 / `realm_level_config` |
| 单位灵气修为 / 灵气吸收 | `spirit_cult_per_unit` | 境界等级配置表 / `realm_level_config` |
| 每时辰产出 | `spirit_rate` | 灵气源配置表 / `spirit_source_config` |

候选单位：

| 中文名 / Chinese | 英文 / English | 换算 / Conversion |
|---|---|---|
| 刻 | `quarter` | 现实 37.5 秒 |
| 时辰 | `game_hour` | 8 刻 = 现实 5 分钟 |
| 游戏日 | `game_day` | 12 时辰 = 现实 60 分钟 |
| 结算周期 | `tick` | 现实 3 秒 |

**这是结构问题不是数值问题**：单位不写在表上，任何人填的数都可能差一个数量级，而且从表面看不出来。

**建议写进字段名**，例如 `base_cult_rate_per_game_hour`、`spirit_rate_per_game_hour`。写在说明行依赖人去读，写在字段名里程序和策划都不可能读错。

### 4.2 边界类型 `boundary_type` 枚举缺「终局」

当前实际取值只有三种，且分布正确：空（自然精进）51 行、`小` 21 行、`大` 8 行。

问题在最后一行：**Lv80 大乘十层填的是「大」**，即大乘圆满后还要做一次大境界突破——但没有下一个大境界，也没有 Lv81。

策划案 §8.2 的边界类型定义本来是四个值，实表只用了三个，缺的正是终局。建议枚举写全并写进类型行 `##type`：

| 中文 / Chinese | 英文 / English | 含义 / Meaning |
|---|---|---|
| （空） | `natural` | 修为满后自然精进，不需要玩家操作 |
| 小 | `stage` | 阶段小突破，需玩家确认，可失败 |
| 大 | `realm` | 大境界突破，需玩家确认，可失败 |
| 终局 | `final` | 等级推进终点，不再有下一级 |

### 4.3 「第一行绝对值、其余行增量」没有声明位

属性列的实际约定是：第 1 行填角色初始绝对值，第 2 行起填每级增量。这个约定表里没有任何地方写，而且第 1 行的绝对值与后段某些行的增量会撞成同一个数，肉眼分辨不出。

**建议拆成两列**，语义写在字段名上：

| 中文名 / Chinese | 英文字段 / Field | 含义 / Meaning |
|---|---|---|
| 属性基础值 | `attr_base` | 角色初始绝对值，只有第 1 行有效 |
| 属性每级增量 | `attr_per_level` | 每提升一级增加的值 |

另：属性槽位是 属性名1、属性名2、**属性名5、属性名6**，缺 3、4。需确认是删列残留（重排为 1/2/3/4）还是有保留用途（在说明行 `##说明` 标明留给谁）。

### 4.4 自然精进行是否携带突破字段

合并表之后，51 个自然精进的等级行也带着基础成功率 `base_success_rate` 和基础虚弱时间 `fail_weakness` 两列。这些等级不需要突破、不会失败、不会进虚弱。

这是合并表必然带来的形态，不是错误，但需要一条写进说明行 `##说明` 的约定：

> 边界类型 `boundary_type` 为空（自然精进 `natural`）时，基础成功率 `base_success_rate` 与基础虚弱时间 `fail_weakness` 必须留空，程序不读取这两列。

有了这条约定，导表工具可以直接校验。

### 4.5 「刻」`quarter` 是新的一级时间单位，藏在备注格里

配置项总表 `config_field_index` 的 基础虚弱时间 `fail_weakness` 那一格的备注里，写了一整段策划规则：虚弱的完整行为定义、「刻 = 现实 37.5 秒」、游戏内要换算成「多少天多少时辰多少刻」显示、「3600 = 游戏内 1 天」的换算基准。

这些是策划规则，不是字段说明，放在备注格里会随表改版丢失。尤其「刻」`quarter` 是策划案 §3.1 固定时间体系里**根本没有的一级单位**，必须回写进正文，见 4.1 的换算表。

### 4.6 虚弱配置表 `weakness_config` 删除的连带影响

该表被删后，虚弱行为写死在代码里，原 7 个可配项只剩 1 个：

| 中文名 / Chinese | 英文字段 / Field | 现状 / Status |
|---|---|---|
| 虚弱ID | `weakness_id` | 已删 / Removed |
| 持续时长 | `duration` | **保留**，并入 `fail_weakness` |
| 基础修为倍率 | `base_cult_multiplier` | 写死 / Hard-coded |
| 直接修为倍率 | `direct_cult_multiplier` | 写死 / Hard-coded |
| 能否吸收灵气 | `can_absorb_spirit` | 写死 / Hard-coded |
| 能否突破 | `can_breakthrough` | 写死 / Hard-coded |
| 恢复丹药组 | `recovery_pill_group` | **丢失 / Lost** |

前四项写死可接受——虚弱行为本来就统一。但恢复丹药组 `recovery_pill_group` 丢失要处理：丹药配置表 `pill_config` 那一侧还留着「虚弱恢复」这个效果目标 `effect_target`，两边对不上。要么在丹药配置表用别的方式表达，要么确认「任何带虚弱恢复效果的丹药都能解任何虚弱」。

### 4.7 其他结构项

| 项 / Item | 现状 / Current | 建议 / Action |
|---|---|---|
| 大境界ID `realm_id` | 整列 80 行全空 | 补齐；它是大境界唯一标识，也是其他系统引用境界的入口 |

## 五、分歧与正解 / Divergence and Resolution

### 5.1 单位灵气修为 / 灵气吸收 `spirit_cult_per_unit` 的语义

| 立场 / Position | 主张 | 理由 |
|---|---|---|
| 小G | 定为角色灵气吸收能力 | 按境界等级配置表现状 |
| 小C | 定为修为转化率 | 定成吸收量则灵气收益被源产出卡死，而基础修为随境界成长，两者不同步，后期灵气源系统失效 |

**这个分歧是假的，正解是两个都要。**

小G 在同一节问了转化效率 `conversion_efficiency` 归谁，但没把两件事连起来：一旦把 `spirit_cult_per_unit` 定成吸收能力，转化基数就无处安放。小C 说「选哪个都缺一个字段」，正确答案不是二选一，而是境界等级配置表把两个都补齐。

**建议的四字段拆分：**

| 中文名 / Chinese | 英文字段 / Field | 归属表 / Owner | 由谁决定 / Determined By | 外部可改 / Externally Writable |
|---|---|---|---|:--:|
| 境界吸收上限 | `absorb_cap_base` | 境界等级配置表 / `realm_level_config` | 境界 / Realm | 否 / No |
| 单位灵气修为基数 | `spirit_cult_base` | 境界等级配置表 / `realm_level_config` | 境界 / Realm | 否 / No |
| 灵气转化倍率 | `conversion_multiplier` | 各系统效果配置 / Owning System | 功法、丹药、洞府设施 | 是 / Yes |
| 灵气源单人闸门 | `per_player_absorb_cap` | 灵气源配置表 / `spirit_source_config` | 灵气源 / Source | 是 / Yes |

角色实际吸收量 = min（境界吸收上限，灵气源单人闸门，源中可分配份额）。

前两个锁在境界表且外部不可写，灵气收益 = 吸收量 × 转化基数，两项都随境界成长，灵气源系统全程有效——而且越往后越重要，不是越来越没用。「吸收率只由境界决定」这条闸门也才真正落到表结构上。

第四个是共享源限制单人独占的手段。**不加的话，共享源里高境界角色会按需求比例拿走绝大部分份额，低境界角色几乎分不到**，秘境会变成高境界专属。要不要这个效果需要拍板。

### 5.2 灵气总产量上限 `spirit_total`

小G 主张保留，小C 主张规则未定先摘掉。小G补充「枯竭是运行规则，不必新增基础字段」——这点同意。

**折中：保留字段，但先补规则。** 需要在策划案里写明：

- 枯竭后是永久消失还是定期刷新，刷新周期由谁配
- 共享秘境被吸干后其他玩家能否进入、界面如何表现
- 累计产量记在源上还是角色上
- WAR3 是开房间的，一局结束即重置——该机制的实际意义是「限制单局内某个源的总产出」，需按此表述
